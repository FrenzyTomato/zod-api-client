# zod-api-client

Generate [Zod](https://zod.dev) schemas and fully typed API clients from an OpenAPI, Swagger, Postman or HAR file. Use the generated clients with Playwright, plain `fetch`, or your existing axios instance. Every successful response is validated against its schema.

```ts
import { createApiClient } from "./generated-api"; // generated by the CLI

// Create the client once; it covers every endpoint, grouped by API tag
const api = createApiClient({ baseURL: "https://api.example.com" });

// api.<tag>.<operation>(...)
const { token } = await api.auth.login({ body: { username: "alice", password: "secret" } });
const pet = await api.pets.getPet(42); // response is validated inside the client and fully typed
await api.pets.registerPet({ body: { name: "Rex", species: "dog" } });
const owners = await api.owners.listOwners({ query: { limit: 10 } });
```

## Features

- **Many input formats**: OpenAPI 3.0 and 3.1, Swagger 2.0, Postman collections and HAR recordings, from a local file or a URL. The format is detected automatically.
- **Typed clients**: one client per API tag, with typed path params, query, headers, cookies, request bodies and responses.
- **Runtime validation**: responses are checked with Zod, so a mismatch between the API and its document fails loudly.
- **Works with any HTTP client**: Playwright's `request` fixture, the built-in `fetch`, or an axios instance (its interceptors still run).
- **One way to send a body**: pass `body` and the client sends JSON, form-encoded or multipart, depending on what the document declares. File uploads accept a `Buffer`, `Blob` or `File`.
- **Deterministic**: generation is pure code transformation, so the same input always gives the same output.

## Supported inputs

| Format | Detected by | Notes |
| --- | --- | --- |
| OpenAPI 3.0 | `openapi: 3.0.x` | YAML or JSON, including relative external `$ref`s. |
| OpenAPI 3.1 | `openapi: 3.1.x` | Converted to 3.0 first (`type: [X, "null"]`, `const`, numeric `exclusiveMinimum`, …). |
| Swagger 2.0 | `swagger: "2.0"` | Converted to OpenAPI 3.0 first. |
| Postman collection v2.0 / v2.1 | `info.schema` | Folders become tags. Schemas are inferred from example bodies and saved responses. |
| HAR (browser or proxy recording) | `log.entries` | Numeric and UUID path segments become path params. Schemas are inferred from recorded traffic. |

## Install

```bash
npm install --save-dev zod-api-client zod
```

Requirements:

- Node.js 18 or newer.
- Zod 4 (4.4.3 or newer).
- `@playwright/test` only if you call the API from Playwright tests.

## Quick start

**1. Add a config file**, `zod-api-client.config.ts`, at your project root:

```ts
import { defineConfig } from "zod-api-client";

export default defineConfig({
  input: "./openapi.yaml",       // or swagger.json, collection.postman.json, capture.har, https://…
  output: "./src/generated-api",
});
```

**2. Generate the client:**

```bash
npx zod-api-client generate
```

Adding it as a script makes regenerating easy:

```json
{
  "scripts": {
    "generate:api": "zod-api-client generate"
  }
}
```

**3. Use it:**

```ts
import { createApiClient } from "./src/generated-api";

// Create the client once. This one object covers every endpoint in the API.
const api = createApiClient({ baseURL: "https://api.example.com" });

const pets = await api.pets.listPets({ query: { limit: 10 } }); // already validated and typed
await api.pets.registerPet({ body: { name: "Rex" } });
await api.owners.listOwners();
```

The CLI generates `createApiClient` into the output folder. Call it once per server or setup, not once per endpoint. Responses are checked against their Zod schemas inside the client, so you never parse them yourself.

Regenerate whenever the API document changes. Don't edit the generated folder by hand.

## Validation in action

Both sides of a call are checked against the schemas from your API document:

- **Responses** are always validated at runtime.
- **Requests** are type-checked by TypeScript as you write them. With the `validateRequests: true` client option, they're also validated at runtime before anything is sent.

```ts
import { ZodError } from "zod";
import { ResponseValidationError } from "zod-api-client/runtime";

const api = createApiClient({ baseURL: "https://api.example.com", validateRequests: true });

// ✅ Valid request, valid response: you get typed, checked data
const pet = await api.pets.registerPet({ body: { name: "Rex", species: "dog" } });
pet.id; // number

// ❌ Invalid request, caught by TypeScript before the code runs
await api.pets.registerPet({ body: { name: "Rex", species: "dragon" } });
//                                                  ~~~~~~~~ not one of "dog" | "cat"

// ❌ Invalid request, caught at runtime (e.g. data from outside TypeScript).
//    Throws a ZodError, and no request is sent.
const input = JSON.parse('{"name": "Rex"}'); // missing required "species"
await expect(api.pets.registerPet({ body: input })).rejects.toBeInstanceOf(ZodError);

// ❌ The API returns a response that doesn't match its schema,
//    e.g. { "id": "42", "name": null } where id should be a number and name a string.
//    Throws a ResponseValidationError instead of returning bad data.
await expect(api.pets.getPet(42)).rejects.toBeInstanceOf(ResponseValidationError);

try {
  await api.pets.getPet(42);
} catch (error) {
  if (error instanceof ResponseValidationError) {
    console.log(error.body);         // the raw response body
    console.log(error.issues); // which fields failed, e.g. [{ path: ["id"], message: "Invalid input: expected number, received string" }]
  }
}
```

Request validation is off by default, so negative API tests can deliberately send invalid input to check the server rejects it:

```ts
const raw = createApiClient(request); // validateRequests defaults to false
// @ts-expect-error: deliberately invalid
await expect(raw.pets.registerPet({ body: { name: "" } })).rejects.toMatchObject({ status: 422 });
```

## Usage

### Creating a client

`createApiClient` is generated by the CLI. You call it **once**, and that one object covers every endpoint in the API. Only create another one to talk to a different server or with different settings (in Playwright, that's one per test, since each test has its own `request`).

It accepts whatever HTTP client fits where the code runs:

```ts
import { createApiClient } from "./src/generated-api";

// Anywhere (scripts, Node services, Jest/Vitest): uses the built-in fetch
const api = createApiClient({ baseURL: "https://api.example.com" });

// Inside a Playwright test: uses the `request` fixture and its baseURL, cookies and storage state
test("lists pets", async ({ request }) => {
  const api = createApiClient(request);
  await api.pets.listPets();
});

// An existing axios instance: its baseURL, auth and interceptors still apply
const api = createApiClient(myAxios);
```

There is one property per API tag (`api.pets`, `api.owners`, …), with one method per operation. Names are camelCased from the document's tags and `operationId`s (or summaries).

### Calling endpoints

Path parameters are positional arguments, in the order the document declares them. Everything else goes in a single request object:

```ts
// GET /pets/{petId}
const pet = await api.pets.getPet(42);

// GET /pets?limit=10&tags=a&tags=b
const page = await api.pets.listPets({ query: { limit: 10, tags: ["a", "b"] } });

// Headers and cookies
await api.pets.listPets({ headers: { "X-Trace-Id": "abc" }, cookies: { session: "s1" } });

// GET /owners/{ownerId}/pets/{petId}
await api.owners.getOwnerPet(ownerId, petId);
```

### Request bodies

Every endpoint uses `body`. The client picks the encoding from the document, so you never choose between JSON, form and multipart yourself:

```ts
// application/json
await api.pets.registerPet({ body: { name: "Rex", species: "dog" } });

// application/x-www-form-urlencoded
await api.auth.login({ body: { username: "alice", password: "secret" } });

// multipart/form-data with a file
await api.pets.uploadPhoto(42, {
  body: { photo: readFileSync("rex.png"), caption: "Rex" },
});
```

File fields accept any of these:

```ts
readFileSync("rex.png");                                          // Buffer / Uint8Array
new Blob([bytes], { type: "image/png" });                         // Blob
new File([bytes], "rex.png", { type: "image/png" });              // File (keeps its name)
{ name: "rex.png", mimeType: "image/png", buffer: readFileSync("rex.png") };
```

If an operation documents more than one request content type, the first supported one is used.

### Responses

The client parses and validates every successful response against its Zod schema before returning it. You get typed data back, with no `.parse()` on your side:

```ts
const pet = await api.pets.getPet(42); // pet is typed, and its shape is already checked
pet.name;
```

If the response doesn't match the schema, the call throws a `ResponseValidationError` instead of returning bad data. Endpoints with no response body return `void`. When an operation has several success responses, the type is a union of them.

### Types and schemas (optional)

You don't need these for API calls, since the client already validates. They're exported for your own code. Each tag has a `<Tag>Schema` namespace in the generated index:

```ts
import { PetsSchema } from "./src/generated-api";

// Reuse the generated types in your own helpers
type Pet = PetsSchema.GetPetResponse;
const describePet = (pet: Pet) => `${pet.name} the ${pet.species}`;

// Check data that didn't come through the client, e.g. a fixture file or a webhook payload
const fixture = PetsSchema.getPetSchema.parse(JSON.parse(readFileSync("pet.json", "utf8")));
```

Request types are `<Operation>RequestType`, response types are `<Operation>Response`, and the Zod schemas are `<operation>Schema` (response) and `<operation>RequestSchema` (request).

### Errors

```ts
import { ApiHttpError, ResponseValidationError } from "zod-api-client/runtime";

try {
  await api.pets.getPet(999);
} catch (error) {
  if (error instanceof ApiHttpError) {
    console.log(error.status, error.body); // non-2xx response; body is parsed JSON when possible
  }
  if (error instanceof ResponseValidationError) {
    console.log(error.issues); // 2xx response that didn't match its schema: the failing fields
  }
}
```

- `ApiHttpError` is thrown for any non-2xx status. It has `status`, `url`, `headers` and `body`.
- `ResponseValidationError` is thrown when a successful response doesn't match its schema or isn't valid JSON. It has `status`, `url`, `body`, `issues` (the failing fields) and `cause` (the Zod error).

In a test:

```ts
await expect(api.pets.getPet(999)).rejects.toMatchObject({ status: 404 });
```

### Client options

Pass options as the second argument, or as the only argument when using fetch:

```ts
const api = createApiClient(request, {
  baseURL: "https://api.example.com/v1",
  timeout: 30_000,
  validateRequests: true,
  beforeRequest(request) {
    request.headers = { ...request.headers, Authorization: `Bearer ${token}` };
  },
});
```

| Option | Meaning |
| --- | --- |
| `baseURL` | Prefix for every request. A path prefix such as `/v1` is kept. |
| `timeout` | Request timeout in milliseconds. |
| `validateRequests` | Also validate requests before sending. Off by default, so negative tests can send invalid input on purpose. |
| `beforeRequest` | Hook to change a request before it's sent, e.g. to add auth or idempotency headers. |

## Configuration

`zod-api-client.config.ts` is found by walking up from the current directory. Paths in it are relative to the config file.

```ts
import { defineConfig } from "zod-api-client";

export default defineConfig({
  input: "./openapi.yaml",
  output: "./src/generated-api",
  paths: ["/pets", "/pets/{petId}"],
  ignoreHeaders: ["X-Request-Id"],
  strict: false,
  har: { hosts: ["api.example.com"] },
});
```

| Field | Default | Meaning |
| --- | --- | --- |
| `input` | | API document path or `http(s)://` URL. |
| `output` | `./generated-api` | Output directory. |
| `paths` | all | Only generate these API paths. |
| `ignoreHeaders` | none | Header parameters to leave out of generated requests (case-insensitive). |
| `strict` | `true` | With `false`, endpoints the generator can't handle are skipped and reported instead of failing the run. |
| `har.hosts` | all | For HAR input, only use requests to these hosts, dropping analytics and CDN noise. |

## CLI

```bash
npx zod-api-client generate [api-document] [options]
```

```text
-c, --config <file>          Use an explicit config file
-o, --output <directory>     Set the generated output directory
    --path <api-path>        Generate one API path (repeatable)
    --ignore-header <name>   Omit one request header (repeatable)
    --lenient                Skip unsupported operations instead of failing
-h, --help                   Show help
-v, --version                Show the package version
```

Examples:

```bash
npx zod-api-client generate ./openapi.yaml -o ./src/generated-api
npx zod-api-client generate https://petstore3.swagger.io/api/v3/openapi.json
npx zod-api-client generate ./capture.har --lenient
npx zod-api-client generate --path /pets --path "/pets/{petId}"
```

CLI options override the config file, and a repeatable option replaces its config array. CLI paths are relative to the current directory.

## Programmatic API

```ts
import { generate } from "zod-api-client";

const result = await generate({
  input: "./openapi.yaml",
  output: "./src/generated-api",
  ignoreHeaders: ["X-Request-Id"],
});

console.log(result.operationCount, result.skipped);
```

## Generated output

```text
generated-api/
  clients/                 one client class per tag
  schemas/                 Zod schemas and types per tag
  index.ts                 createApiClient, plus re-exports
  .zod-api-client.json     marker listing generator-owned files
```

Generation won't overwrite a non-empty folder it didn't create. On later runs, it only replaces or removes files it generated, so unrelated files in the folder are left alone.

## Limitations

- **Postman and HAR give looser types.** They contain examples rather than schemas, so the inferred types have no enums or formats, every parameter is a string, and HAR path params are named `id`, `id2`, and so on. Prefer an OpenAPI document when you have one.
- **Some HTTP features aren't supported.** Methods other than GET, POST, PUT, PATCH and DELETE are not supported, nor are some parameter styles (such as `deepObject`). Use `--lenient` to skip those endpoints.
- **Path parameters `.` and `..` throw a `TypeError`.** URLs treat them as relative path segments, so no HTTP client can send them.
- **Passing `cookies` with Playwright replaces the context's stored cookies** for that call, because it sets the `Cookie` header.
- **Set a path prefix on `createApiClient`.** A path prefix set only on a Playwright context's own `baseURL` is dropped by Playwright, because generated paths start with `/`. Pass it as the `baseURL` option of `createApiClient` instead.
